# 0.9.0-A round-trip validation — status

See `0.9.0-A_results.json` for the machine-readable detail this summarizes.

## What's verified

All 5 fixtures, authored in real Microsoft Excel for Mac (16.108), edited via elixcee,
saved both ways (save-as and in-place), reopened in real Excel:

| fixture | content | VBA | result |
|---|---|---|---|
| 1 | values, formula, style, merge, hidden row/col | no | clean, formula recalculated live to correct value |
| 2 | VBA macro | yes | clean; macro *execution* blocked by an environment issue (see below) |
| 3 | table, data validation, conditional formatting | yes (incidental) | clean; all three silently dropped (known gap) |
| 4 | hyperlink, comment, defined name | yes (incidental) | clean; all three silently dropped (known gap) |
| 5 | chart, image, print area | no | clean; chart/image/print-area silently dropped (known gap) |

**No repair warning, no "cannot open" error, no `vbaProject` loss, no relationship
breakage, no in-place-save failure — for any of the 5 fixtures, either save mode.** This
is **1 fixture set, 1 cycle per save mode** — the exit criteria call for 10+ consecutive
cycles per mode, not met yet.

## Bugs found and fixed this round

All three found by fixture 1 specifically — none of the pre-existing hand-built Rust test
fixtures happened to include a formula cell, a theme part, or a non-macro `.xlsm` output,
so nothing caught them until real Excel refused to open the file.

1. **Formula flattening** (`de2ee3f`) — every untouched formula cell silently lost its
   formula on save. `ELIXCEE_DATA_LOSS`.
2. **Orphaned relationships** (`1ea4066`) — `xl/theme/theme1.xml` and
   `docProps/{app,core}.xml` passed through byte-identical but their relationships were
   dropped from the regenerated `.rels` files. `ELIXCEE_RELATIONSHIP_BREAK`.
3. **Wrong `.xlsm` content type** (`1ea4066`) — the dominant cause of the "cannot open"
   error: a non-macro `.xlsm` output declared the plain (non-macro) content type instead
   of the macro-enabled one the `.xlsm` extension requires, regardless of content.

All three fixed, covered by new Rust regression tests (`cargo test --workspace`: 828+
passing) and `mechanical_check.py`'s self-test (7 negative-calibration cases).

## Known gap confirmed, not a new bug

Fixtures 3, 4, and 5 all hit the **same root cause**: `build_xlsx_sheet` fully regenerates
`xl/worksheets/sheetN.xml` from `Vm`'s cell state on every save, and only knows how to
emit `<cols>`/`<sheetData>`/`<mergeCells>`. Anything else embedded in worksheet XML —
tables, data validation, conditional formatting, hyperlinks, comments — is silently
dropped. `xl/workbook.xml` being fully regenerated the same way also drops defined names.
The underlying *part* (e.g. `xl/tables/table1.xml`, a chart, an image) usually survives as
inert bytes, orphaned rather than deleted.

**This was already disclosed** in the 0.8.0 safe-round-trip milestone's own Non-goals
section ("anything embedded in a regenerated `xl/worksheets/sheetN.xml` does not
survive"). 0.9.0-A's real-Excel testing didn't discover a new defect here — it confirmed,
with concrete real-Excel evidence, exactly what was already documented as out of scope,
and confirmed the important secondary fact: **none of this causes a repair warning**.
Excel just silently has less content than before.

Fixing this is real feature work — re-injecting known worksheet-embedded elements into the
regenerated XML, or moving to a diff/merge writer instead of full regeneration — matching
the scope of a future milestone, not attempted this round.

## Macro execution: not evaluable this round

Running `fixture2`'s macro fails with "Microsoft Visual Basic: license information for
this component was not found" — reproduced **identically from Excel's own Macro dialog
(⌥F8), against the untouched original file, before elixcee ever touched it.** Ruled out:
not a `codeName`/binding issue (the macro resolves and lists correctly), not specific to
external `run VB macro` invocation (fails from inside Excel's UI too), not caused by
anything elixcee wrote. This is a Mac Excel/VBA-runtime environment issue on this specific
machine — the same class of unexplained instability the prior session's
`MACOS_APPLESCRIPT_EXPLORATION.md` already flagged and left unresolved. Out of scope to
chase further this round.

## Harness

- `compat/oracle-excel-com/mechanical_check.py` — structural OOXML validator (ZIP entries,
  content-types, relationship completeness in both directions, vbaProject byte-identity)
  plus a semantic formula-preservation check. Self-test corrupts 7 different ways before
  trusting any real result.
- `compat/oracle-excel-com/fixtures/{pristine,work}/` — pristine fixtures committed,
  read-only; `work/` (gitignored) is where every actual test run edits/saves.

## What's not done

- **10 consecutive open/save/reopen cycles per fixture per save mode** — only 1 done so
  far for fixtures 2–5. Fixture 1 additionally chain-tested at **5 consecutive in-place
  saves on the same file** (stricter than 5 independent cycles — any state-accumulation
  bug would compound): `mechanical_check.py` clean after every cycle, real Excel reopen
  after cycle 5 confirmed values/formula(recalculated to 1110)/merge all still correct.
- **AppleScript cannot create tables, data validation, conditional formatting,
  hyperlinks, or charts** — confirmed empirically (`-50` parameter errors), despite being
  documented in Excel's own `.sdef`. All 5 fixtures' non-trivial content (fixtures 2–5)
  was authored manually by the user in Excel's UI instead.
- **Macro execution verification** — blocked on the environment issue above, not on
  anything in elixcee.
