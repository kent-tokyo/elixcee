## Bugs found and fixed along the way

All three were found by this fixture specifically — none of the pre-existing hand-built
Rust test fixtures happened to include a formula cell, a theme part, or a non-macro
`.xlsm` output, so nothing caught them until real Excel refused to open the file.

1. **Formula flattening** (`de2ee3f`) — every untouched formula cell silently lost its
   formula on save, replaced by a stale literal. `ELIXCEE_DATA_LOSS`.
2. **Orphaned relationships** (`1ea4066`) — `xl/theme/theme1.xml` and
   `docProps/{app,core}.xml` passed through byte-identical but their relationships were
   dropped from the regenerated `.rels` files. `ELIXCEE_RELATIONSHIP_BREAK`.
3. **Wrong `.xlsm` content type** (`1ea4066`) — the dominant cause of the "cannot open"
   error: a non-macro `.xlsm` output declared the plain (non-macro) content type instead
   of the macro-enabled one the `.xlsm` extension requires, regardless of content.
   `EXCEL_REPAIR_REQUIRED`-class, but in practice Excel refused to open the file at all.

All three are fixed, covered by new Rust regression tests (`cargo test --workspace`: 828+
passing) and by `mechanical_check.py`'s self-test (7 negative-calibration cases, including
one added for each new bug class this round).

## Harness built

- `compat/oracle-excel-com/mechanical_check.py` — structural OOXML validator (ZIP entries,
  content-types, relationship completeness in both directions — dangling AND orphaned —
  vbaProject byte-identity) plus a semantic formula-preservation check. Pure stdlib, no
  Excel needed; this is the fast, repeatable primary signal. Self-test deliberately
  corrupts 7 different ways and asserts each is caught, before trusting any real result.
- `compat/oracle-excel-com/fixtures/{pristine,work}/` — pristine fixtures committed,
  read-only; `work/` (gitignored) is where every actual test run edits/saves.

  macro). Getting VBA content into a fixture at all requires one manual step: AppleScript
  has zero VBA-project manipulation surface (confirmed, see
  `MACOS_APPLESCRIPT_EXPLORATION.md`) — the only way in is VBA's own
  `VBProject.VBComponents.Add`/`CodeModule.AddFromString`, which itself needs an
  already-present macro to invoke it. A blank pristine workbook has no such macro to
  bootstrap from. This is a real constraint, not a process shortcut — it needs one
  manual VBE paste of a small bootstrap macro into a fresh workbook, after which the rest
  (author, edit, verify, repeat) can proceed via AppleScript as it did for fixture 1.

  to the Excel work above; reports byte count + diff-vs-baseline in the CI summary,
